# 截图库存抵扣与石墙默认计算修复

## 截图已读清却未抵扣

故障记录中的物品数量为 `readable`，槽位独立，但 `region_kind=unknown`。旧逻辑要求先辨认背包、箱子或工具柜等具体容器，导致整批读数被过滤，再被错误描述为“截图没有清晰读数”。

现在将 `kind=inventory`、具体容器未知的格子默认视为玩家局部库存。已辨认物品、可读数量及唯一槽位可参与本轮抵扣，无需填写档案或逐项确认。容器未知时不宣称完整盘点；制作目录、场景物品、身份不明、读不清、重复槽位及无法去重的多图仍不合并。明确的他人或历史图片仍遵循原有上下文边界。

自动库存保留逐项 `excluded_observations` 原因，识别详情据此说明未计入的原因。没有可用项时不再声称已采用清晰读数，也不把所有排除原因都写成数字不清。旧草稿在后续使用时重新归一化，保留原观测时间；原先保存的回复不会自动重写。

视觉提示补充容器未知时保留库存、物品身份与数字分别核对的要求。更新识别缓存键，避免新上传复用旧提示的结果；保留接口探测配置标识，不要求因本次提示调整重新验证接口。提示改进不保证每个图标识别正确。

## 石墙缺省条件被错误拒绝

引擎原本支持 `hp=null` 时从规则目录读取满血值；故障发生在模型解析返回 `unsupported`，导致请求未到达引擎。

常见中文墙/门省资源比较采用严格整句匹配，直接构造计算请求：默认一面、硬面，血量由目录读取。不在文本规则中硬编码伤害、成本或结果。带受损、实际血量、指定武器、修改服等额外条件的句子不走这条快捷路径，仍进入完整模型解析和校验。模型提示也明确省略血量与明确受损的区别，“最省资源”默认比较已收录单一方案的新增硫磺。

从制作切换到明确拆除任务时，清除旧制作请求与待补充上下文；当前有效截图仍可提供库存。随后补充血量会沿用拆除目标。正文展示满血假设；局部库存参与排序时说明未计入的物品可能影响缺口和排序。

## 验证

`uv run pytest -q`：464 项通过，包含原始六项识别结果、未知容器、局部覆盖、正文与详情、旧草稿重新归一化、制作十个 C4 后紧接石墙比较、两面墙与不同门类、特殊条件不被覆盖及补充血量。

可选真实接口复测会向已配置的模型发送指定图片，使用临时数据库，不改动原有会话：

```sh
uv run python docs/run_inventory_raid_smoke.py path/to/inventory.png --live
```

连续验证制作十个 C4、拆一面石墙，以及“它还剩250血”。结果保存到忽略提交的 `data/inventory-raid-smoke.json`，应核对实际物品身份、抵扣数量和最终回复；自动断言不等同于人工确认每个图标。

本次已使用故障原图跑通真实接口：具体容器仍被识别为 `unknown`，但工具实际抵扣金属碎片 550、硫磺 140、木炭 4、布 50，十个 C4 的剩余需求为电子零件 20、金属碎片 1450、低品质燃油 600、硫磺 21860、木炭 29996。未显示数量的金属物品没有计入。后续石墙请求按 500 HP 返回两个 C4，补充 250 HP 后返回一个 C4；沿用截图硫磺后新增硫磺分别为 4260、2060。本轮计算不会扣除真实背包，后续预算也不假定上一轮已经执行。

# Rust 游戏 AI Coach Agent：六层架构面试讲稿

核实日期：2026-11-05（北京时间）。实现基线：Git 提交 `e8d0a3e` 加核实期间工作区已有的观测／计量相关未提交更新；这些并行更新不是本次讲稿任务的修改。

使用方式：第一部分可直接口述，按约 12—15 分钟组织；小标题不必读出，实际时长需以个人语速试讲。第二部分用于复习，第三部分供追问时查证，不纳入口述时间。Rust 在本文中指生存游戏。

## 一、面试主讲稿

### 开场：我想帮玩家解决什么问题

我做的是一个面向 Rust 生存游戏的 AI 教练。玩家经常遇到的问题是：背包里有一些材料，但不知道能做什么、还缺什么；或者有几个发展方向，不知道现在应该先做哪件事。我希望玩家可以直接说话、发截图，让系统结合当前情况，给出有依据的计算和建议。

我用六层来解释这个项目：输入、理解、知识、决策、生成，以及评测与观测。它们是六种职责，不是每次都要经过的六道工序。应用有网页入口，后端用流程图控制分支，本地数据库保存对话和状态。明确的计算直接交给计算工具；配方解释可以查本地知识；需要取舍的问题才进入建议流程。记录机制贯穿处理过程，离线评测则单独运行。

下面我用一个例子串起来：玩家上传背包截图，问“合成一个 C4 还差哪些材料”。C4 是游戏里的一种爆炸物，制作它还需要先做一些中间材料，所以这不只是查一张配方表。

### 输入层：先把玩家提供的信息接稳

我首先要解决的是，文字和图片怎样进入同一次请求。网页先上传图片，拿到属于当前会话的图片引用，再把引用和原始问题一起交给后端。代码检查消息长度、图片数量、文件格式和像素大小，也检查图片是不是属于这个会话、是否已经过期。图片会统一方向和格式，保存规范图与缩略图；这些步骤不需要模型。

真正看懂图片时，才调用视觉模型。它结合问题和相关上下文，识别可见物品、数量、格子位置，也判断截图是在说本人、对手，还是过去的情况。在这个例子里，它还可以提出“制作一个 C4”这个任务候选。因此，图片处理虽然在路由之前执行，里面已经包含了一部分语义理解。

模型返回后，代码检查结果结构、图片引用、物品是否在目录中，以及数量和格子是否满足后续使用条件。数量模糊时，有条件地裁剪局部再读一次。最后交给理解和计算环节的是带来源的观测，不只是几个脱离图片的数字。

我没有要求玩家每次先填时间、逐格确认。没有相反说明时，系统按当前本人截图理解，这样问材料缺口比较顺畅。但这是默认假设，不是实时游戏数据。结构检查也不能证明图标认对了；模型把一种材料认成另一种、又表现得很确定，仍然可能通过检查。

### 理解层：把一句话变成能继续处理的任务

拿到文字和截图观测后，我需要判断玩家现在要做什么。当前实现先用代码识别明确命令、常见说法和上下文变化，再决定去计算、查知识、看状态、给建议，还是普通聊天。需要解析复杂计算条件时，才让语言模型提取目标和数量；视觉模型已经给出可用目标时，也可以直接接上计算。这里并不是所有路由都由一个大模型自由决定。

对于 C4 的例子，后续需要的是“制作什么、制作多少、采用哪份库存”。如果玩家接着说“改成两个”，系统保留任务并修改数量；如果改问拆墙，就切换计算类型；说“取消”，就结束当前计算。更正截图读数时，系统保留原识别，生成新的分析记录。规则没有覆盖的表达仍可能理解失败，所以条件不明确时会请玩家补充。

接下来是整理可用库存。代码从截图中挑出身份可辨、数量可读、格子不重复的物品，再检查是不是当前本人信息。只拍到部分背包，也可以按已知材料计算，但必须保留“还有未计入库存”的条件。多张图或多个区域不会直接累加，避免重复算同一批材料。如果文字、截图或选定的档案容器同时提供库存，代码会要求明确采用一个来源，不会擅自把它们相加。

我把当前任务、玩家档案和长期记忆分开管理。任务及其计算条件随对话保存，方便下一轮继续；截图观测和继承的文字库存都有时效，不能因为还能找到记录，就一直当作当前库存。代码能识别的当前状态补充先形成临时视图，可以覆盖本轮的旧条件，但不直接改档案。档案按服务器和清档周期区分，清档就是服务器重置这一轮游戏世界。一般修改需要明确保存；已经关联档案时，明确报告本人死亡或背包丢失则是例外，代码会先让旧背包失效并清零，保留回执和历史。

长期记忆保存的是表达偏好、习惯和自报经历。明确偏好可以由规则提取，其他合格内容可以在回答后由模型提取候选，再由代码核对引文和允许保存的类别。它帮助我少讲重复内容，却不能拿来抵扣库存，也不能因为讲过某个知识点就认定玩家掌握了。这样做需要维护不同记录，但能避免把“以前有过”和“现在还有”混在一起。

### 知识层：给计算和建议提供不同类型的依据

任务明确以后，我再看它需要什么知识。C4 材料缺口使用的是本地固定规则，包括配方、每批产出和工作台条件。计算工具按物品查规则，并核对依赖的知识是否仍被允许使用，不需要先联网，也不需要让模型凭记忆补配方。目前这些数据对应一个明确的演示快照，还没有认证它适用于最新游戏版本。

如果玩家追问“为什么要这些材料”，系统会进入本地知识解释分支。代码先按物品精确找到配方，再用全文搜索找库存抵扣、批次取整等相关解释；全文搜索就是在已收录的文字中匹配相关内容。代码还会排除撤回或不适用的资料，限制返回内容的长度，再直接组织解释。有需要核算的取整问题，也会再调用计算工具。这条分支不依赖模型生成事实，更没有接入向量数据库。

策略建议使用另一条取证路径。模型可以提出需要了解的主题，代码再根据预设主题搜索、抓取允许来源的网页正文，保存来源、抓取时间和正文快照。搜索不可用时，在允许联网的配置下，还会尝试读取已登记的相关网页；明确关闭联网则不会抓取。没有读到正文，就不能把搜索摘要当成依据。

这些资料返回建议流程后，模型负责解释和权衡，代码负责检查引用能不能在已读正文里找到。网页有出处，仍不代表结论一定适用于玩家的版本；今天抓到的网页也可能讲的是旧机制。固定规则和网页证据因此各有适用范围。玩家状态和历史对话则由前面的会话、档案和记忆服务提供，不会为了统一检索而混进配方知识里。

### 决策层：先算清楚，再讨论该怎么做

回到一个 C4 的例子，理解层已经给出了目标和可用库存，计算器就沿着配方逐层展开。它先抵扣已有成品，再抵扣中间材料，只对剩余部分继续算原材料；多个目标共用的材料会一起处理，并按实际批次向上取整。如果玩家声明了保留材料，也会先留出这部分。

这里全部由算法执行。工具返回缺口、抵扣了哪些库存、制作顺序、批次余量，以及工作台和配方解锁条件。库存未知时，我只能给总需求；只知道部分库存时，我给基于已知材料的条件缺口。材料够不够，与工作台等级、配方是否解锁，是不同问题。整个计算只是模拟预算，不会真的扣减玩家档案中的材料。把这部分交给工具，能让同样输入得到可重复的结果，代价是只支持已经收录的规则和计算范围。

建议类问题会多走几步。比如玩家问“现在应该先加固基地，还是推进科技”，模型先提出少量互为替代的候选，并标明需要哪些状态和资料。代码要求其中保留一个观察、核对信息的选项；随后按需取证。涉及已支持制作配方的候选，分别调用计算器；其他策略则检查关键状态是否缺失、有没有可引用的资料。当前工具并不能把整个基地加固和科技发展的所有成本都精确算完。

这些检查结果连同资料正文交回模型，由模型选出建议和替代方案，解释收益、代价、前提和停止条件。代码再检查候选是否存在、引用原文是否匹配，以及有没有把条件性结论说成确定可行。候选预算彼此独立，不能把几个替代方案当成一次共同花费。这里的程序流程是“提出候选、取证、计算、检查”；回答中的游戏行动步骤，是告诉玩家接下来可以做什么，两者不是一份计划。

当前一般建议走的是固定流程。规划或回答校验失败时，共享一次修复机会，用完就返回说明；它不会不断搜索、重新规划直到成功。新手开局有专门分支：先读攻略，再让模型组织阶段路线，并另请模型核对引用能否支持路线；修复额度用完后，尝试有依据的预置讲解或说明失败。模型复核仍是一次判断，不是事实认证。这样的范围比较容易控制和排查，但还不是能自主解决任意复杂任务的通用执行器。

### 生成层：让结论好懂，同时保留它成立的条件

前面得到结论后，我要解决的是怎样让玩家先看到自己关心的答案。C4 这条计算分支，由代码把缺口清单和必要条件写成摘要，把完整配方过程、识别详情和来源放到可展开的详情里，不再让语言模型重写数字。如果只用了截图中能辨认的材料，回答会说明这个范围；还有其他材料时，实际缺口可能更少。

建议分支里的理由和行动步骤由模型组织，最终再由代码把它们与预算、可行性状态和引用装配到一起。普通聊天才主要由模型直接写回复。表达偏好和已有学习记录可以影响语言、详略和解释方式，但计算数字与预算范围由代码块保留。当前实现中，建议的取舍和叙述是在同一次模型调用里完成的，所以这是职责上的分层，并不是六个彼此完全独立的服务。

我也加了实际的输出检查，比如检测虚构操作回执、过度保证和部分不允许的数值表达，检查引用原文，以及检查受保护的数据和区块有没有变化。普通聊天不通过时最多修复一次，仍不通过就给固定的替代回复；建议有自己的修复额度。提示词还要求不编造事实，但这些检查没有覆盖所有语义，不能据此承诺回答绝对正确。代码能保住一个数字没有被改写，不能证明它最初依据的截图或规则就一定正确。

### 评测与观测层：既知道答得怎样，也知道哪里出了问题

我把评测和观测分开。评测回答“系统有没有做对”，主要在开发时单独运行。理解方面检查任务有没有选对、追问有没有继承正确条件；状态方面检查旧图、对手库存和失效背包有没有被排除；计算方面检查配方展开、抵扣、批次和数值；建议及表达方面检查前提、引用、条件说明和是否直接回答问题。

已有离线测试会固定模型返回，让真实应用流程运行，这能验证代码如何处理输入，却不能证明模型识图准确。库存评测进一步保留原图标注、模型观测、实际采用的库存和最终回答，并用独立整理的配方依据核算。这样能区分“图认错了”和“账算错了”，也能看到错误是否真正影响了最终缺口。没有可靠标注或适用版本依据的地方，保留待核实，不算作通过。

保存的真实模型记录就出现过这样的情况：把齿轮认成电子零件，后面的计算对错误库存算得很一致，最终给玩家的缺口却不对。所以我不能只检查算术，也不能用程序测试通过率替代产品准确率。表达评测还可以另调模型评分，但目前使用同一配置的模型，评分需要人工校准；库存记录中的表达复核也不能冒充独立人工盲评。这些都不是每次回答之后自动执行的一套总评分。

观测则跟随实际请求运行。入口、识图、路由、检索、计算和生成等位置会产生阶段记录；模型和网页调用还单独记录每次尝试、耗时、失败以及服务返回的用量。回到 C4 的例子，我可以查看是否用了旧识别、是否发生局部复读、用了哪份库存，以及时间花在识图还是计算。后台记忆另有记录并关联原请求，不能把重叠的耗时简单相加。

这些记录保存在本地数据库，诊断页面可以查看；网页等待时也显示实际执行阶段，最终正文完成后再整体展示。它目前是一套本地排查能力，没有完整的生产告警平台。缺少用量就记录未知，没有价格和账单就不能声称花了多少钱。我选择先把失败和调用记录清楚，才能决定该改识别、状态管理，还是等待时间。

### 收尾：项目价值和下一步

这个项目的核心价值，是把自然输入、当前情况、游戏依据和可核算的结果接起来。模型负责看图、理解和解释，代码负责来源边界、计算和保存，最后让玩家知道建议依据了什么、还缺什么条件。

下一步我会优先做两件事：用更多独立标注的截图验证识别错误和下游影响，并补足关键规则的版本核验；再根据真实请求的耗时与调用记录，改进慢路径和整次请求的预算控制。这样改进以后，既能比较回答是否更可信，也能比较玩家是否少等了一些时间。

## 三、核实依据与重要边界

### 3. 主案例的可复查依据与数据生命周期

正文的“一张当前本人背包图，询问制作一个 C4”是已接入路径的示意，不声称本次调用了真实视觉模型。数据实际经过：

**原始问题和图片引用 → 视觉观测及制作目标 → 当前本人、有效且不重复的可读库存 → 本地配方展开与抵扣 → 条件缺口及制作限制 → 代码摘要、详情和过程记录。**

这条路径不需要策略候选规划、网页搜索或模型润色；视觉已经给出合格目标时，也不必再调文本模型重复提取。解析失败、来源冲突或条件缺失时，可以返回补充说明，并保留任务供下一轮继续。

需要具体数字时，可采用本次通过的 `test_same_turn_c4_answers_first_with_quality_warning_and_recognition_details`：固定视觉返回木炭 4、硫磺 140，库存为局部；制作一个 C4，在演示快照默认配方且未展开燃油的条件下，木炭缺口是 2996，硫磺缺口是 2060。这只是完整清单中的两项。它证明当前代码与测试预期一致，**不证明真实图片包含这些材料，也不证明最新游戏版本规则相同**。正文省略材料数，以免干扰主线。

自动截图观测用于当前库存的有效期为 30 分钟；默认视觉草稿保存 24 小时，附件保留 168 小时。记录仍在，不等于库存仍有效。继承的文字库存也按 30 分钟处理，死亡、换档案和新信息还可能提前使旧输入不再被采用。一般状态字段按各自有效期投影；当前明确补充形成临时事实，并可能在同范围后续对话中继续使用，不是永久改档案。

截图更正生成新的分析草稿，原始记录保留。服务端另有确认／保存接口，检查本人、时效、档案版本等条件后才写入；当前主聊天页默认发送文字与图片引用，不应把“有保存接口”讲成“每轮必须确认保存”。档案新版本、知识包变化和网页证据过期也会影响后续复用；保存回答前还检查关键版本是否变化。

### 5. 影响讲稿的重要文档差异

1. **流程图里的通用重规划不是当前一般建议链路。** [决策层设计](/c/Users/dokivot/rust-coach-v3/docs/architecture-decision-layer.md:3)描述执行器、状态化循环和有限重规划；实际一般建议图是规划、取证、评估、组织回答、结束，只有局部修复。图片模型也已经在路由前参与任务理解，不能把全部语义理解机械挪到“理解层”。
2. **统一回答契约还不是生成服务唯一入口。** [生成层设计](/c/Users/dokivot/rust-coach-v3/docs/architecture-generation-layer.md:3)描述最终结果到回答规格再到渲染。实际装配直接读计算、建议、视觉和偏好；回答规格是在装配末尾生成并记录的。建议取舍与叙述在同次模型调用完成，未选候选预算也可能进入详情，不能说内部状态已经被完全隔离。
3. **本地知识已接入，但没有统一四库与向量检索。** [知识层差距](/c/Users/dokivot/rust-coach-v3/docs/architecture-knowledge-layer.md:327)中的统一记忆等目标不能全算已实现；当前有规则目录、版本知识包、精确与全文检索。固定规则描述由规则目录生成，是一致性和可追溯记录，不是独立外部交叉验证。
4. **截图强制确认是历史交互。** [多模态修订说明](/c/Users/dokivot/rust-coach-v3/docs/multimodal-design.md:5)已注明自动使用调整；实际可以直接用可读观测进行条件计算。自动用于本轮、玩家确认、保存到档案是不同动作。
5. **观测已有实际接入，但记录仍有限。** [评测观测文档映射](/c/Users/dokivot/rust-coach-v3/docs/architecture-evaluation-observability-layer.md:231)还保留“没有统一跨层 trace”的旧概括。当前有架构事件和独立性能记录；架构事件的结束时间、时长为空，耗时要从性能记录读取。失败请求可能没有最终回合，但有独立性能记录；写入失败或进程中断仍可能造成不完整。

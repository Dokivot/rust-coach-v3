# 意图理解与玩家状态：深度审查与修复

日期：2026-11-05。范围：目标1意图理解/路由、目标5玩家状态建模及其效果证据。库存效果验证的上一轮审查见 `inventory-evaluation-audit-2026-11-05.md`。

## 结论

已经形成真实的端到端工程闭环，可以作为有明确边界的面试演示：输入经过单一任务判断和来源资格检查，进入确定性计算，状态事件有持久回执，回答发布检查档案版本及会话绑定。此次审查发现的阻塞问题已修复并有回归测试；不能据此宣称任意玩家表达都能被正确理解，也不能把固定夹具通过率解释成真实模型准确率。

初始全量测试559项通过，但新增首批18个对抗检查中16个失败、2个通过，随后新增3个检查也暴露缺口。说明原有绿色测试遗漏了事实资格、否定语义、来源选择和并发切换。当前增加21个对抗检查及4个真实冒烟判定器检查。修复过程中保留了原来的来源冲突契约：界面选择容器并附图仍需澄清；自然语言明确“只用档案背包”才排除其他库存。

## 十个审查维度的判断

1. **目标实现**：任务切换、血量补充、死亡后清零、跨会话读取确实改变执行与结果，不仅增加展示字段。强度限于受支持任务和表达。
2. **端到端流转**：HTTP/SSE → ChatRuntime → 事件事务/任务状态 → 工作流路由 → 来源门禁 → 计算/建议 → 版本检查 → 回答与工作状态保存。测试读取真实临时SQLite数据库并核对回执、输入和结果。
3. **可靠输入与约束**：主体、时间、完整性、来源冲突、科技前提都有独立门禁；模型提供候选结构，不能自行认证事实。`/calc` 是用户显式结构化条件，仍需规则与Schema校验。
4. **推断与事实**：图片推断、用户确认、文本自报、档案观测有不同来源；自报并非遥测认证。临时事实有TTL且不隐式覆盖持久档案。`verified` 应解读为当前规则与输入下的计算结果，不能替代蓝图检查或游戏内核验。
5. **静默失败与伪成功**：此次修复了否定误写、部分更正、过时档案发布和只检查输入的评测伪成功。多来源与无证据输入返回明确错误/澄清。
6. **异常降级**：抽取失败有限重试，规则/条件不充分返回 `needs_input`；多义图像纠正返回422；生成中状态变化返回409。模型失败不撤销已提交事件，同请求重试利用回执幂等，避免重新清空后来盘点的背包。
7. **用户价值证据**：测试验证“仍是原拆墙任务”“背包实际清零且基地箱子保留”“只算总需求无抵扣”“工作台不足”“硫磺缺口随死亡变化”，不是仅检查接口200。
8. **复杂度**：一个活动任务、一套来源解析器、SQLite事务与版本检查足够覆盖当前场景。没有引入多Agent、通用规划器、向量数据库或第二套记账系统。正则语义覆盖和重复元数据是维护成本，需要用失败案例驱动，不继续堆架构。
9. **面试价值**：能从“模型输出像答案”推进到可追踪、可拒绝、可重试、可复算的业务行为；可现场展示绿色测试遗漏的问题、反例、修复和独立层次的证据。
10. **追问风险**：真实玩家分布、否定/省略等长尾语言、图像准确性、确认来源的真实性、已知条件与可执行性标签、跨进程并发都需要清楚界定。

## 限制与后续优先级

- 自报和图片都不是游戏遥测；历史/否定/假设检查是保守规则，并非中文全语义识别。未见表达仍可能误判，需要真实玩家样本、人工金标和持续反例集。
- “如果我有100硫磺”目前可能要求澄清，尚无独立的假设情景状态；不应把它写为实际库存。
- 单次6轮真实文本冒烟不是统计准确率、稳定性SLA或真实视觉评测。本次没有新增真实视觉模型、完整浏览器或真实游戏内验收。
- 当前规则是固定第三方PC原版快照，未认证具体游戏build。蓝图未知时可以计算材料，但不能承诺玩家此刻能制作；工作台不足也允许给出预算并显式标记阻塞。
- 只有一个活动计算任务；临时自报及任务不跨会话复制，档案按服务器/清档共享。在线时长是观测值，不自动倒计时；不做资源消费自动记账。
- SQLite版本与绑定检查覆盖已测试竞争，仍需针对多进程并发、恢复和长会话开展专项测试；本次没有生产负载证据。

## 面试官可能的五个追问

1. **40/40为什么不能说明Agent准确率100%？** 固定模型输出和合成截图用于隔离工程链路，只能证明这些契约满足；真实模型6轮冒烟单独报告。泛化需要独立真实样本、人工标注、误差分类和置信区间，不能混算。
2. **如何防止模型把猜测变成事实？** 模型只抽取候选；应用校验来源、当前性、主体、数量与科技文本证据。未知库存与零库存分开，推断图片保持条件性，无证据不计算。玩家自报仍只代表自报，不冒充外部认证。
3. **死亡后模型超时，状态到底保存了吗？** 事件在模型调用前独立事务提交并保留回执；失败明确说明状态已保存，重试按请求身份幂等。死亡后新盘点不会被同请求二次清空，基地仓库按策略保留。
4. **模型生成时玩家换服或修改档案怎么办？** 生成使用快照，保存回答的事务同时核对scope绑定及revision。任一不一致拒绝发布，返回409让用户重试，不能只看旧scope的revision。
5. **为什么不用更复杂的Agent规划系统？** 当前主要是单任务切换和条件更新，显式任务状态、确定性工具与SQLite足够可解释。优先把来源、异常和证据做实；支持多任务协作或长程恢复时再根据需求扩展。现有正则长尾覆盖不足应靠真实评测推动改进，不能靠增加Agent数量掩盖。

# 代码生成就绪度评审

> 范围更新：本文保留骨架生成前的评审记录。当前已生成基础聊天骨架；用户已明确将游戏业务规则、业务验收样例和计算器调研推迟到后续阶段，它们不是首版聊天服务的启动前置条件。当前实施现状见 [首版实施说明](scaffold.md)。下文“当前项目只有设计文档”等描述对应评审时点。

评审对象：[架构设计 v2](architecture.md)、[决策流程](plan-and-execute.mmd)、[RAG 流程](agentic-rag.mmd)、[整体架构](architecture.mmd)及当前项目文件。日期：2026-11-01。

## 1. 结论

**目前达到“可以生成项目骨架和接口占位”的程度，尚未达到“可以直接、稳定地生成完整可运行业务系统”的程度。** 不需要重做总体架构，下一步应补充实施规格，把已经确定的原则变成类型、状态转换、判定规则、接口协议和可执行验收案例。

当前项目只有设计文档、图与制图脚本，没有服务源码、依赖锁文件、数据库迁移、提示词模板、知识种子或业务测试。文件缺失本身不说明必须先手写这些代码；但对应的**实现选择与完成标准**必须明确，才能让代码生成过程不自行发明产品行为。

| 生成目标 | 当前是否足够 | 说明 |
|---|---|---|
| 目录、抽象接口、节点函数占位、基础配置 | 基本足够 | 框架版本等常规工程选择仍需固定 |
| 能用固定假数据回放的工作流原型 | 不足 | 缺字段级契约、唯一转换规则、mock 结果与断言 |
| 接真实向量检索和实时搜索的决策 MVP | 不足 | 还缺 provider 配置、初始语料、提示词和业务策略 |
| 满足生产可靠性与质量要求的服务 | 不足 | 需要集成/恢复/质量/性能实测，不能只靠文档确认 |

“计算器暂不实现”是明确范围，不是设计遗漏。首次代码生成可以包含两个 Port 和返回 unavailable 的占位 adapter；不能把接入计算器列为启动决策 MVP 的强制前置条件。

## 2. 已经足够明确、不必重新讨论的部分

- 模块化单体；Runtime、Graph、Domain、Tools、状态、记忆、知识和持久化分工。
- 决策采用 Plan-and-Execute；Agentic RAG 作为证据获取子流程，具备向量检索与实时搜索。
- 两类计算独立短路径，未配置时不产生精确数字。
- 玩家状态、会话、长期记忆分开；任务级 checkpoint 支持中途澄清。
- 版本/来源追溯、有限重试/重规划、预算、部分结果和评测方向。

真正缺的是这些原则的可执行定义，而不是更多抽象层或更多框图。

## 3. P0：批量生成业务代码前应补齐

P0 表示缺失会直接影响模块接口或业务行为，不代表必须先写完全部实现。以下内容可以收敛到一份 implementation-spec.md 加少量 schema/prompt/fixture 文件，不必拆成大量文档。

| 项目 | 当前依据与缺口 | 最小补充产物 | 完成标准 |
|---|---|---|---|
| 1. 首个可交付切片 | §17 有阶段，但没固定首版目标平台、入口、图片是否实接、部署形态 | MVP 能力矩阵：真实能力、占位、明确不支持；至少一个贯穿案例 | 每种请求知道能做什么、如何降级；不暗中取消向量或实时搜索要求 |
| 2. 字段级数据契约 | §4–5、§9–10 是字段名/字段组，尚非可验证 schema | Pydantic/JSON Schema 级定义及合法/非法 JSON；类型、必填、默认、单位、unknown、枚举、版本 | 每个节点/工具交接能结构校验，未知库存与零库存不同 |
| 3. Graph 执行规格 | §6–7、§9 定义节点职责，但未给每个节点精确读写、路由优先级与 reducer | 节点表、转换表、父子 State 映射、初始化/清理/合并规则 | 同一输入状态得到唯一合法路径；重复恢复不丢成果/复用旧结果 |
| 4. 可执行业务规则 | §7.3 的硬约束、Pareto、行动目录尚未实例化；§9 的“充分/冲突”仍是原则 | 小而真实的 ActionCatalog、条件谓词、槽位策略、证据覆盖策略、排序/平局规则 | evaluate_actions 和 assess_coverage 不依赖模型临时编造门槛 |
| 5. 模型节点契约与提示词 | 已明确哪些节点是 G，但没有 system/task 模板、示例、输出修复规则 | 意图、Planner、Replanner、query、grade、rewrite、表达的模板与输出 schema | 可用录制输出独立驱动图；无效输出、缺字段、拒答有确定处理 |
| 6. API 与事件协议 | §13.2 只有 API 类别和事件名称 | 路径/方法、请求响应、HTTP 错误码、SSE envelope、幂等与 resume 契约 | 客户端无需猜测如何创建、订阅、回答澄清、取消与重连 |
| 7. 持久化与执行生命周期 | 有表名/租约/预算原则，缺表关系、唯一键、事务和调度方案 | ER/迁移规格，任务调度、checkpoint/结果事务、租约、预算结算和故障时序 | 进程重启后知道谁恢复什么；调用结果与预算不会重复提交 |
| 8. 外部依赖契约与运行配置 | 已有技术栈推荐，但无锁定版本、模型/embedding/search 选型与方法签名 | Runtime 版本/锁定策略、Port async 签名、错误映射、配置项、开发运行方式 | 能生成可安装工程和 fake adapter；真实 adapter 有明确映射目标 |
| 9. 可执行验收样例 | §14 有测试主题，但没有输入、工具返回、预期状态/输出 | fixture 集、Given/When/Then、节点/路径断言、独立期望值来源 | 能据此判断生成代码是否正确，而非仅“能启动” |

### 3.1 最重要的数据对象

需要定型的边界对象包括 CoachRequest/Response、PlayerSnapshot/ObservationPatch、IntentSpec、TaskState/DecisionState/RagState、ExecutionPlan/Step/Result、ActionSpec/Plan、EvidenceNeed/Ref/Bundle/Grade、ClarificationRequest/ResumeRequest、ToolResult、两类计算请求/响应、AnswerSpec、BudgetReservation、TaskEvent。

重点不是把字段名称再列一遍，而是消除歧义：

- unknown、missing、conflicting、stale 是否是不同状态；null、空列表、0 各代表什么。
- 时间是否统一 UTC、ID 如何生成、数值与单位如何表达、拒绝补充和输入“不知道”如何编码。
- ToolResult 使用按 status 区分的结构，避免 unavailable 同时携带可被渲染为真实结果的 quantities。
- EvidenceBundle 中的 context_changed、新 snapshot revision、证据定位结构必须成为正式字段，而非只出现在叙述中。
- 对外 DTO 可用 Pydantic；Graph State 使用适合 LangGraph channel/reducer 的 TypedDict 等。二者边界需明确，不机械用同一个对象兼任数据库模型和全图状态。

### 3.2 每个节点需要的最小规格

记录：读哪些字段、返回哪些 patch、调用什么依赖、是否有副作用、何时计预算、成功/错误/缺信息的返回形状、下一跳、幂等键、恢复时重执行语义。以 verify_step 为例，不能只写“验证后继续”：

| 输入情况 | 建议明确的决策（需在实施规格定稿） |
|---|---|
| 成功且仍有依赖满足的步骤 | 保存结果并前进；何时将 running 改为 succeeded 要明确 |
| 已配置工具报告需要玩家字段 | 保存澄清 payload，当前步骤 waiting_input |
| 工具未配置 | 标记能力不可用；按该步骤是否影响核心目标选择 conditional/partial，不能等价于缺输入 |
| 新状态使已完成结果过期 | 标记受影响依赖 stale，选择重算或重规划 |
| 预算耗尽 | 保存已有有效成果，进入部分结果，不自动新建子任务 |

这张示例表说明所需精度，不代表所有节点规则已经补完。

### 3.3 业务规则不能全部留给代码生成临场发挥

至少选择一组代表性行动定义，如检查入口、修复已知缺口、盘点相关材料、确认工作台、推进一个已明确的科技目标；每个定义前置条件、所需证据和未知条件如何处理。首批具体游戏机制必须来自审核资料，不为凑规则杜撰游戏数值。

还需明确谁生成、谁批准 required_claims 和 success_criteria。如果让 Planner 自己定义全部必需证据再自行删减，系统可能检索到一点相关资料就宣布完成。建议以受支持任务/行动模板提供不可删除的最小要求，模型只能扩展或提出修改，最终由规则验证。

RAG 至少固定：什么算版本兼容、来源可信范围、证据足够/矛盾/未知的编码、何时强制 web、无新增证据时是否还允许首次转 web、grader 失败时是否放行、空 required_claims 是否拒绝。初始策略可以简单，但必须确定且可测试，不需要等到最优阈值。

## 5. P1：真实集成前必须落定，但不阻塞接口骨架

### 5.1 模型、embedding、搜索与存储

选择一个默认模型及结构化输出方式、embedding 模型/维度、实时搜索供应商、正文提取方式、PostgreSQL/pgvector 版本和本地/生产文件适配。provider 名称可配置，但首个真实 adapter 不能只有“可替换”四个字。

密钥只通过环境或 secrets 配置，不放在提示词或项目文档。无密钥的开发模式使用明确标记的 fake，真实运行模式缺配置应 fail fast 或返回能力不可用，不能静默装作真实搜索成功。

### 5.2 初始知识和行动资产

需要一小批覆盖首个纵向案例的真实、可审核来源：原文、适用版本、策略卡、分块样例、实体别名、来源/审核状态、release manifest，以及从导入到查询的可重复流程。只有向量库表结构没有数据，无法验证决策质量。

公开来源清单、允许使用的范围、更新责任、时效窗口需落实。向量检索与 web 都要至少有一次真实集成验证；fake 只能证明编排，不证明检索有效。

### 5.3 状态和前端入口

落实首版用户通过什么方式提供背包/基地/科技信息，如何呈现需要补充的字段、如何提交 resume。可以先用 API/简单客户端验证，不必先做完整 UI。若图片本轮不实接，应显式列为未启用能力，不默认文本链路已经满足多模态。

## 6. P2：上线前验证，不必阻挡第一轮生成

大规模金标和专家质量门槛、模型选择对比、长期知识更新 SLA、部署规模、成本/延迟压测、备份恢复、保留策略、正式身份系统和权限隔离都需要后续验证。关键恢复/幂等/隔离逻辑的契约是 P0，完整生产运维验证是 P2，不能因为后者可晚做而省略前者。

暂不需要新增微服务、多 Agent 协商、专用图数据库、复杂长期记忆平台，也不需要先实现真实计算器。相关能力保持预留，不等于靠 LLM 临时代替。

## 7. 最小验收集合与生成顺序

第一批 fixture 建议至少覆盖以下场景，每个写出输入、当前 State、模拟依赖结果、预期下一跳/输出、不得发生的行为：

1. 本地知识足够：完成决策，不多余联网。
2. 本地没有证据：仍能进入首次 web；正文支持后继续。
3. 显式“这次更新”：主动实时搜索，旧缓存不能冒充核验。
4. 搜索摘要有答案但正文不可用：不把摘要当充分证据。
5. 决策执行一步后才缺玩家字段：同 task 暂停/恢复，已完成步骤不重复。
6. RAG 子图中断：恢复后查询轮次、证据和预算不重置。
7. 新回答改变玩家 revision：仅依赖它的结果 stale，再评估/重规划。
8. 用户拒绝或不知道：有限澄清后 partial/条件结果，不猜状态。
9. 两个计算接口未配置：分别返回 unavailable；不产生数量或伪计算记录。
10. Replanner 修改剩余计划：保留有效成果，不能删核心目标和硬约束。
11. assemble/request_information 步骤：状态正确推进，不提前完成、不无限重复。
12. 重复 resume、并发写、工具超时与全局预算耗尽：幂等、单写者、有效退出。

上述是待建立案例清单，不是本次已执行的业务测试。需要给每项配具体数据和断言，不能原封不动变成测试函数名就算完成。

推荐交付顺序：

1. 固定首版切片和图文歧义，定型 schemas、状态转换、规则/提示词与协议。
2. 用少量明确 fixture 生成 contracts、空 adapter、fake dependencies 和三个图的可运行回放。
3. 用一个最小 LangGraph/PostgreSQL 技术验证确认嵌套中断、重复子图调用、崩溃恢复和版本兼容，再批量扩展实现。
4. 接 pgvector 与真实 web、导入首批知识，完成“已有状态 → 计划 → 取证 → 中途补充 → 恢复 → 建议”的贯穿案例。
5. 按证据而非代码行数验收，后续单独调研接入计算器。

## 8. 谁需要决定什么

产品侧需要明确：首个平台/ruleset、首版是否实接图片、预期使用入口/身份范围、首批建议场景及必须优先满足的玩家目标；如果外部服务/数据使用存在组织限制，也要给出约束。

工程侧可以直接提出默认值并记录：字段类型、文件结构、数据库索引、错误码、reducer、模型与搜索 adapter 的接口、兼容版本、测试工具。无须把所有技术细节变成用户选择题；只对会改变产品范围或外部服务约束的选择征求意见。

本次评审没有替用户更改范围、接入供应商或实现服务。它确认的是：**总体架构足以指导开发；补齐“契约 + 执行语义 + 业务规则/提示词 + fixture”后，才适合一次性生成可验收的 MVP。**

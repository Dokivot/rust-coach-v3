# 库存效果验证深度审查

审查时间：2026-11-05 05:20（Asia/Shanghai）。基线提交：`99f1a7d`。审查对象是“用数据证明 Coach 答得对”的库存与制作评测闭环；历史模型输出保持不变。

## 结论

评测工程本身已形成可用的小闭环，能证明某一轮在限定事实、规则和复核条件下通过、失败或证据不足；它没有证明 Coach 整体答得对。已保存真实批次为9案例、12轮、19次模型调用，最终5失败、3待核验、1通过。这个结果适合展示“如何发现错误前提下的自洽答案”，不适合包装成准确率成果。

## 按严重程度的问题

### P0：目标措辞与真实结果不一致

- 发生位置：`evals/results/inventory-acceptance-v2-reviewed-2026-11-05.json`、`presentation-materials/goals/G07-效果验证/brief.md`。
- 核心影响：当前数据证明的是评测器能发现错答，而不是 Coach 已经可靠；若面试时说“证明答得对”，会被9例中仅1例通过直接反驳。
- 暴露场景：追问成功率、保留集结果或要求现场打开失败案例时。
- 修改方式：展示口径固定为“证明回答在什么条件下成立，并暴露不成立”；业务修复后必须用新的未见图片、冻结配置和重复运行做前后对照。
- 面试阻塞：阻塞“Coach 已可靠”的展示；不阻塞“评测与 Agent 诊断能力”的展示。

### P1：行为配置不完整可能产生伪可比（已修复）

- 发生位置：`evals/inventory_baseline.py` 的实时报告配置和 `evals/inventory_evidence.py` 的版本比较。
- 核心影响：旧报告未记录 `vision_detail`、指令角色、上下文窗口和视觉输出上限；这些参数不同仍可能被判为可比。
- 暴露场景：换成 `original` 视觉 detail、缩短历史窗口或改变指令角色后做版本对照。
- 修改方式：新增 `evaluation-configuration-v2`，冻结全部关键行为配置；比较仍对配置对象做严格相等检查。
- 面试阻塞：修复前阻塞可信的版本收益对照；修复后新运行不阻塞，旧报告继续标为历史部分配置。

### P1：文档中的标准测试命令无法运行（已修复）

- 发生位置：`evals/README.md` 的 `uv run pytest ...`、`pyproject.toml`、缺失的 `evals/__init__.py`。
- 核心影响：此前“517项通过”依赖未声明的 `PYTHONPATH`/虚拟环境差异，按文档执行会在收集阶段失败，属于可复现性伪成功。
- 暴露场景：新机器、CI 或面试现场直接执行 README 命令。
- 修改方式：将项目根目录加入 pytest `pythonpath`，并把 `evals` 声明为包。
- 面试阻塞：修复前阻塞现场演示；当前命令可直接通过。

### P1：捕获清单不防重复或案例错配（新运行已修复）

- 发生位置：`evals/inventory_baseline.py` 的实时报告与 replay。
- 核心影响：没有计划清单时，截断或重复的 runs 仍可能被重判并汇总，造成样本缺失或重复计数而不报错。
- 暴露场景：报告复制、人工合并、进程中断后误把部分文件当完整结果。
- 修改方式：新报告写入案例选择、重复次数和计划运行数；重判校验运行唯一性、案例定义、artifact 结构及新格式清单。
- 面试阻塞：新运行已不阻塞；2026-11-05 旧捕获没有计划清单，只能验证9条运行身份与唯一性，不能倒写历史证据。

### P1：测试只证明机制，未锁定真实用户价值（已修复）

- 发生位置：`tests/test_inventory_evaluation.py`。
- 核心影响：合成 fixture 能证明代码运行，却不能防止判定器改动后把真实错答误判为通过。
- 暴露场景：修改依赖传播、视觉评分或复核合并逻辑时。
- 修改方式：新增保存真实批次回归，强制验证 `components_craft` 首错在视觉、错误库存下算术虽通过但正确库存缺口失败，并验证未知 HP 案例才是通过。

### P2：规则版本仍未认证

- 发生位置：`evals/inventory-acceptance-v2.json` 的 `oracle.version_status` 与 raid provisional 状态。
- 核心影响：配方手算与 Wiki 快照一致，不等于目标游戏 build 一定适用；制作结果因此保持 pending。
- 暴露场景：游戏更新配方、服务器 mod 或面试官追问数据时效。
- 修改方式：明确目标 build/服务器规则，保存同版本官方说明或受控游戏测试记录，再把状态改为 verified。
- 面试阻塞：阻塞“当前版本数值正确”；不阻塞展示独立 oracle 与 pending 传播。

### P2：表达复核不是独立人工盲评

- 发生位置：`evals/results/inventory-acceptance-v2-review-2026-11-05.json`，`reviewer_kind=coding_agent`。
- 核心影响：事实与算术有自动锚点，但表达完整性和澄清合理性仍带单一评审偏差。
- 暴露场景：面试官追问 evaluator bias 或 LLM-as-judge 可靠性。
- 修改方式：请熟悉 Rust 的独立评审按冻结 rubric 盲评，计算一致率并保留分歧裁决。
- 面试阻塞：不阻塞工程展示；阻塞把主观表达质量作为强结论。

### P2：样本量和独立性不足

- 发生位置：`evals/inventory-acceptance-v2.json` 的 source group 与一次重复。
- 核心影响：只有两个新独立图片场景，且首次运行后已成为已见样本，无法证明泛化、稳定性或总体准确率。
- 暴露场景：模型波动、提示词调优后复测同图、要求置信区间时。
- 修改方式：新增未参与调试的保留图源，按风险分层抽样并至少重复3次；报告关键错误率和误拒率，不只报通过率。
- 面试阻塞：阻塞泛化结论；不阻塞小型诊断闭环。

### P2：端到端止于 ASGI，不是浏览器验收

- 发生位置：`evals/inventory_baseline.py` 的 transport 描述与 E2E 测试。
- 核心影响：上传、SSE、持久化已覆盖，但前端附件选择、渲染和用户可见错误未进入证据链。
- 暴露场景：浏览器事件解析、UI 状态或静态资源回归。
- 修改方式：增加一个固定浏览器 smoke，保存输入、最终可见回答和失败截图；仍与模型质量指标分开。
- 面试阻塞：不阻塞后端 Agent 评测展示；阻塞“完整用户链路已验收”。

### P3：证据报告体积偏大

- 发生位置：`evals/results/*reviewed*.json`，多份报告重复嵌入模型调用与轮次数据。
- 核心影响：审查成本高、Git diff 噪声大，但没有改变判定正确性。
- 暴露场景：后续样本和重复次数增长时。
- 修改方式：长期改为不可变 raw capture + 内容寻址 artifact + 小型派生 assessment；当前不为九例引入数据库或平台。
- 面试阻塞：不阻塞；保持现状比现在平台化更简单。

## 面试官可能追问及建议回答

1. **为什么只有1例通过还说目标完成？** 建议回答：完成的是可信评测闭环，不是质量达标；结果明确阻止我声称 Coach 已可靠，下一轮要修业务并用新保留集证明收益。
2. **为什么不用另一个模型直接打分？** 建议回答：模型评审适合补表达维度，但库存格子和材料算术需要独立事实锚点；否则 judge 可能与被测模型共享同一错误。
3. **怎么证明首错归因不是猜的？** 建议回答：我说的是“按轮次与依赖找到最早有证据的分歧”，不是因果根因；真正因果需要干预实验，例如替换正确视觉输入后重跑下游。
4. **如何证明修复后真的变好？** 建议回答：冻结 oracle、grader、配置和预算，在未见 source group 上做业务版本成对运行并重复采样，同时报告关键错答、覆盖损失和无谓澄清。
5. **为什么不直接建设完整评测平台？** 建议回答：九例阶段的瓶颈是事实标准和保留样本，不是存储；本地 JSON 闭环已经能定位问题，等样本、团队和发布频率增长后再迁移内容寻址 artifact 与统一 trace。
